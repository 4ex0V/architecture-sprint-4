# Выбор и настройка мониторинга в системе

## Мотивация
Мониторинг - базовый инструмент для понимания происходящего в любой информационной системе. 
Приобретения компании от внедрения мониторинга:
1. Наблюдение трендов утилизации ресурсов
2. Выявление узкие мест в различных частях системы
3. Алертинг по заранее настроенным правилам при обнаружении каких-то специфических аномалий
4. Сбор бизнес-метрик

Мониторинг полезен не только инженерам для устранения технических проблем, а еще и бизнесу, предоставляя ему инструмент для анализа.

## Выбор подхода к мониторингу
Важный момент заключается в необходимости реализовать мониторинг как для прикладных сервисов, так и для инфраструктурных сервисов. Это означает, что могут, но не обязательно, использоваться разные подходы к мониторингу.

Для прикладных сервисов, работающих по запросам, логично использовать метод **RED**, т.к. нам важна скорость и минимум ошибок.

Для сервиса расчёта стоимости изделия лучше использовать метод **Четыре золотых сигнала**, т.к. он подходит под пакетную обработку данных.

Метод **USE** будем использовать для мониторинга инфраструктурных сервисов, таких как RabbitMQ, Database, 3d files storage.

## Метрики
### 3.1 API-сервисы
1. **Number of requests (RPS)**  
   - **Зачем**: «Traffic» из «четырёх сигналов»; позволяет оценить активность пользователей
   - **Метки**: http_method (GET/POST/etc), http_code (200/404/500/etc)

2. **Response time (latency)**  
   - **Зачем**: проверка на соответствие SLA. Медленный сервис - плохой сервис; возможно, нужны оптимизации (кеширование)
   - **Метки**: url, http_code

3. **Number of HTTP 500**  
   - **Зачем**: количество ошибок на сервере. Увеличение сигнализирует о том, что что-то работает не так, как ожидалось
   - **Метки**: service_name, url

4. **CPU %**
   - **Зачем**: падает отзывчивость сервиса при загрузке CPU выше ожидаемых значений; может перестать обслуживать запросы при превышении порогов
   - **Метки**: service_name

5. **Memory Utilization**
   - **Зачем**: падает отзывчивость сервиса, если он часто собирает мусор (сваливается в FullGC); может перестать обслуживать запросы при исчерпании памяти (Out of Memory)
   - **Метки**: service_name

### 3.2 RabbitMQ
1. **Number of dead-letter-exchange letters**  
   - **Зачем**: отражает, сколько сообщений не смогло обработаться по ожидаемому pipeline'у. Увеличение количества может сообщить о наличии каких-то кейсов, к которым система не готова или вообще не предназначалась
   - **Метки**: service_name, exchange_name, queue_name

2. **Number of messages in flight**  
   - **Зачем**: отражает, сколько сообщений в очереди обрабатывается в текущий момент. Если значение стабильно высокое, то это означает, что потребители нуждаются в оптимизации/масштабировании.
   - **Метки**: queue_name

### 3.3 Базы данных
1. **Number of connections**  
   - **Зачем**: важная метрика для понимания нет ли утечки соединений
   - **Метки**: database_name (db per service)

2. **Memory Utilisation**  
   - **Зачем**: при нехватке памяти запросы обрабатываются медленнее
   - **Метки**: database_name (db per service)

3. **Size of DB instance**  
   - **Зачем**: проактивный контроль занятости дисков для подготовки к увеличению (закупки железа занимают длительное время)
   - **Метки**: database_name (db per service)

### 3.4 Хранилище (S3)
- **Size of S3 storage**  
  - **Зачем**: проактивный контроль занятости дисков для оценки затрат на хранение в S3
  - **Метки**: s3_storage


## План действий
1. Запуск инфраструктуры мониторинга (ELK/Prometheus/Grafana)
2. Настроить необходимое логирование на сервисах: прикладное, access-логи, логи контейнера. Включить filebeat.
3. Настройка dashboard'ов и алертов/триггеров
4. Организация доступа (при наличии чувствительных данных)

## Насыщенность
Показатели насыщенности:
1. **Утилизация CPU**
   
   При достижении порогового значения - 80-90%, т.е. когда текущая нагрузка начинает оказывать существенное влияние на работу всех пользователей - можно предусмотреть автоматическое масштабирование средствами облачного провайдера, вертикальное или горизонтальное.

2. **Использование памяти, в %**

    Аналогично предыдущему пункту.

3. **Время ответа**

    Предлагается мерить время ответа с помощью перцентилей и когда происходит повышение какого-то ожидаемого порога, т.е., например, 95% запровов начинает обратываться выше ожидаемого SLA, начать автоматический алертинг в мессенджеры и/или дозвон ответственным/дежурным разработчикам.

4. **Количество сообщений в dead-letter-exchange letters**

    Аналогично предыдущему пункту: если копится большое количество сообщений - пороговое значение любое > 0 - в очереди "сломанных" сообщений, то это сигнал, что что-то идёт не так и следует оповестить разработку об этом. 
    Точное пороговое значение зависит от прикладной области: если это какая-то статистика - её можно "потерять", а если это пользовательский заказ - нельзя.

5. **Количество сообщений в очереди**
    
    При устойчивом росте количества сообщений в очереди это может означать что потребитель "отвалился" от очереди из-за каких-то проблем. Следует оповестить ответственных в автоматическом режиме.
