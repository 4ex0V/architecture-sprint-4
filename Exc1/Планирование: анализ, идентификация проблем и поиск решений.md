# Планирование: анализ, идентификация проблем и поиск решений

## Существующие проблемные места
1. Жалобы пользователей, что они не получили заказ
2. Жалобы пользователей на длительное выполнение заказа
3. Жалобы операторов на долгую прогрузку первой страницы MES

## Потенциальные проблемные места
1. Отсутствие кеширования для ускорения работы системы
2. Отсутствие реплики БД
3. Отсутствие кластеризации сервисов
4. Отсутствие CI/CD
5. Отсутствие мониторинга и трейсинга для анализа проблем
6. Длительное тестирование и исправление обнаруженных ошибок

## Инициативы
1. Внедрить мониторинг и логирование для сбора информации о работе системы
2. Выделить в новую компоненту функционал расчета стоимости изделия, т.к. она самая затратная по CPU. После выделения она может быть легко масштабируема в зависимости от нагрузки средствами используемого облачного провайдера и силами DEVOps-инженера
3. Разделить API на внешнее (EAG - External API Gateway) и внутреннее (IAG - Internal API Gateway)
   1. Настроить rate limiter для EAG
4. Внедрить централизованное управление статусами заказов (Temporal/Saga)
5. Внедрить кеширование данных для компоненты MES
6. Разделить БД по сервисам (вместо 1 общей БД использовать отдельный инстанс для каждого сервиса) и предоставить API для взаимодействия между сервисами
7. Перевести ручные тесты на автоматизированные
8. Настроить CI/CD
9. Разобрать release среду или использовать её для других целей (автотестирование).

##  Архитектура через полгода
Информационная система, которая представляет собой кластеризованный за балансировщиком набор сервисов, где каждый сервис имеет  реплицированную и/или шардированную БД; собирает логи, имеет мониторинг и алертинг. Сервисы кешируют свои данные и имеют API с документацией. Покрыты юнит и интеграционными тестами.
Статусы заказов обрабатываются в одном месте с помощью Temporal.
Внешняя потенциональная нагрузка отделена от внутренней; сложные расчет отделены в отдельную компоненту и автоматически масштабируются на стороне облачного провайдера в зависимости от нагрузки.
Все изменения в код вносятся через PR/MR, выполняется автоматическая сборка артифакта, прогоняются тесты и, затем, автотесты. Релизная сборка раскатывается через green/blue деплой.
